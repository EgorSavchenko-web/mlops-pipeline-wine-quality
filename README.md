# PMLDL Assignment 1 — Deployment

An end-to-end MLOps pipeline that re-runs itself **every 5 minutes**: it cleans
the raw data, retrains a model, packages it into a Docker image, and restarts a
model API and a web application in two separate containers.

**Dataset:** [Wine Quality (red)](https://archive.ics.uci.edu/dataset/186/wine+quality), UCI — 1 599 red wines, 11 physico-chemical measurements.
**Task:** binary classification — will a taster panel score this wine **6 or higher**?
**Model:** `RandomForestClassifier` (scikit-learn).

| Component | URL once the pipeline has run |
|---|---|
| Streamlit application | <http://localhost:8501> |
| Model API (Swagger UI) | <http://localhost:8000/docs> |
| Airflow UI | <http://localhost:8080> — `admin` / `admin` |
| MLflow run history | <http://localhost:5000> |

---

## 1. Architecture

```
                    ┌──────────────────────── Airflow (scheduler, every */5 min) ───────────────────────┐
                    │                                                                                   │
 data/raw/*.csv ──► │ data_engineering ──► model_engineering ──► deploy_api_and_app ──► smoke_test ──► prune │
                    │       │                     │                      │                             │
                    └───────┼─────────────────────┼──────────────────────┼─────────────────────────────┘
                            ▼                     ▼                      │ docker compose up -d --build
                   data/processed/         models/model.pkl              │ (host Docker daemon via /var/run/docker.sock)
                     train.csv              models/metrics.json          ▼
                     test.csv               mlruns/  (MLflow)   ┌──────────────┐      ┌──────────────┐
                                                                │  pmldl-api   │◄─────│  pmldl-app   │
                                                                │  FastAPI     │ HTTP │  Streamlit   │
                                                                │  :8000       │      │  :8501       │
                                                                └──────────────┘      └──────────────┘
```

The Airflow containers mount the host's Docker socket, so the API and app
containers are **siblings** of Airflow rather than nested inside it. That is why
their published ports land directly on `localhost`.

## 3. Prerequisites

* **Docker Desktop** (Windows/macOS) or Docker Engine + Compose v2 (Linux).
  On Windows, install it with the WSL 2 backend and make sure the whale icon in
  the tray says *Engine running* before continuing.
* **Git**.
* At least ~6 GB of free disk space and ~4 GB of RAM available to Docker.
* Python 3.11 locally is optional — needed only to open the notebook.

## 4. Running the pipeline

```bash
git clone https://github.com/EgorSavchenko-web/mlops-pipeline-wine-quality.git
cd mlops-pipeline-wine-quality

# Build the Airflow image and start the stack (first build: 3-6 minutes)
docker compose -f services/airflow/docker-compose.airflow.yml up -d --build

# Watch it come up
docker compose -f services/airflow/docker-compose.airflow.yml ps
```

Open <http://localhost:8080> and log in with `admin` / `admin`. The DAG
`pmldl_wine_quality_pipeline` is unpaused on creation and fires on the next
5-minute boundary; press ▶ *Trigger DAG* if you do not want to wait.

The **first** run also downloads `python:3.11-slim` and installs scikit-learn
inside the API image, so it takes a few minutes. Every later run reuses those
layers and finishes in well under a minute.

When the run is green, open:

* <http://localhost:8501> — enter measurements (or pick a preset), press
  **Predict**, and the verdict comes back from the API container;
* <http://localhost:8000/docs> — the same model, called directly;
* <http://localhost:5000> — one MLflow run per pipeline execution.

### Stopping

```bash
docker compose -f code/deployment/docker-compose.yml down            # API + app
docker compose -f services/airflow/docker-compose.airflow.yml down   # Airflow
```

Add `-v` to the second command to also drop the Airflow metadata database.

## 5. Running a stage without Airflow

Useful while developing, and the fastest way to see what each stage produces:

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows;  source .venv/bin/activate on Linux/macOS
pip install -r requirements.txt

python code/datasets/prepare_data.py     # → data/processed/{train,test}.csv
python code/models/train_model.py        # → models/model.pkl + metrics + MLflow run
docker compose -f code/deployment/docker-compose.yml up -d --build
```

## 6. Pipeline stages

### Stage 1 — Data engineering (`code/datasets/prepare_data.py`)

| Operation | What it does |
|---|---|
| Load | Reads `data/raw/winequality-red.csv`, auto-detecting `,` vs `;` and tolerating a BOM. |
| Clean | Normalises column names; drops 240 duplicate rows (identical readings would leak across the split); median-imputes any missing cell; removes rows outside a 3·IQR fence on any feature — 139 rows, ~10%. |
| Split | Binarises `quality ≥ 6` into `is_good`, then a **stratified** 80/20 split. |

Outputs `data/processed/train.csv` (976 rows), `test.csv` (244 rows) and
`data_report.json` — an audit trail of exactly what was dropped and why.

### Stage 2 — Model engineering (`code/models/train_model.py`)

Feature engineering adds four domain-derived columns to the eleven raw ones
(total acidity, bound-sulfur ratio, alcohol/density, acidity/alcohol). The same
function serves the API, which is what keeps training and serving in step.

A 200-tree `RandomForestClassifier` is trained, then evaluated on the held-out
test file. Typical run:

| metric | value |
|---|---|
| accuracy | 0.787 |
| precision | 0.805 |
| recall | 0.792 |
| F1 | 0.798 |
| ROC-AUC | 0.861 |
| 5-fold CV F1 (train) | 0.763 |

Parameters, metrics and the model card are logged to the MLflow file store in
`mlruns/`, and the model is packaged with `joblib` into `models/model.pkl`
alongside a `model_card.json` that pins the exact feature order, sklearn
version and training timestamp.

The model binary is attached to every MLflow run as well, so a run can be
reproduced from the tracking store alone. That costs disk: one run every five
minutes is roughly 1.2 GB of `mlruns/` per day. Set `LOG_MODEL_BINARY = False`
in `train_model.py` before leaving the pipeline running unattended for days —
the model card is logged either way, so each run still records which model it
produced.

The stage then **verifies its own artefact** before handing it downstream: it
reloads the pickle and compares predictions with the in-memory model, and scans
the bytes for references to modules the API image does not install (`dill`,
`cloudpickle`, `__main__`). A model that would die on startup in the API
container fails here instead, with a message that says why.

### Stage 3 — Deployment (`code/deployment/`)

`docker compose up -d --build` builds two images from the repository root:

* **`pmldl-api`** — FastAPI + uvicorn. The trained model is `COPY`ed into the
  image, so a new model literally means a new image. Endpoints: `/health`,
  `/model`, `/metrics`, `/predict`, `/predict/batch`. Inputs are validated by
  Pydantic against physically plausible ranges.
* **`pmldl-app`** — Streamlit. Eleven numeric inputs, two presets, a **Predict**
  button and a result area, plus a sidebar showing live API health and the
  current model's test metrics. It holds no model and reaches the API only by
  its service name, `http://api:8000`.

### Automation (`services/airflow/dags/pmldl_pipeline_dag.py`)

```
data_engineering → model_engineering → deploy_api_and_app → smoke_test → prune_dangling_images
```

`schedule="*/5 * * * *"`, `catchup=False`, `max_active_runs=1` (a slow run
delays the next one rather than stacking concurrent Docker builds),
`dagrun_timeout=20 min`. The timeout is deliberately generous, because when it
fires Airflow marks the run's unfinished tasks **skipped** rather than failed —
the pink cells in the grid view — and a cold first build on a new machine
legitimately takes several minutes.

Stages 1 and 2 run as **separate processes** rather than being imported into
the worker. Beyond keeping the repository's top-level `code/` directory from
shadowing Python's standard-library module of the same name, this is what keeps
the trained model clean: the Airflow worker has `dill` imported, dill patches
the standard pickler process-wide, and a model dumped in that process carries
`dill._dill` references that the slim API image cannot resolve.

`deploy_api_and_app` prints container state and the last log lines of both
containers on every run, successful or not — a container that dies on startup
otherwise surfaces in Airflow as the single word `unhealthy`.

`smoke_test` is the proof that the deployment really works: it waits for the API
container to answer, then runs a prediction **from inside the app container**,
addressed to the api container over the shared Docker network.

`prune` deletes the untagged images the rebuild orphans, which would otherwise
grow by gigabytes over a day of 5-minute runs — but only those older than a day.
That filter matters: Compose falls back to the classic builder here, and the
classic builder keeps its layer cache **as untagged intermediate images**, which
an unfiltered prune would delete. The cost of getting this wrong is measurable —
a build with the cache evicted reinstalls scikit-learn, scipy and streamlit from
PyPI and takes two to nine minutes, against roughly twenty seconds with the cache
intact.

## 7. Troubleshooting

| Symptom | Fix |
|---|---|
| `docker: command not found` in the deploy task | The Docker socket is not mounted, or Docker Desktop is not running. Restart Docker Desktop, then `up -d` the Airflow stack again. |
| Deploy task fails with a permission error on `/var/run/docker.sock` | The Airflow services run as `user: "0:0"` for this reason — confirm that line is still present in `docker-compose.airflow.yml`. |
| Ports 8000 / 8501 / 8080 / 5000 already in use | Change the left-hand side of the `ports:` mapping in the relevant compose file. |
| First run times out | It is downloading base images. Re-trigger the DAG; the second run uses the cache. |
| `/health` reports `degraded` with a `ModuleNotFoundError` | The model was pickled in a process holding an import the API image lacks. Stage 2 guards against this; if you changed how training is invoked, make sure it still runs in its own process. |
| Deploy task fails with `container pmldl-api is unhealthy` | Read the diagnostics the task prints below the build output: container state (including `OOMKilled`) and the API's own logs. |
| Containers die or restart at random | Docker Desktop → Settings → Resources → Memory. Airflow, Postgres, MLflow and the two deployment containers need roughly 6 GB between them. |
| `apache/airflow:2.10.5-python3.11` not found | Use `2.10.5-python3.12` — the pinned libraries support it too. |
| API image build fails on `COPY models/model.pkl` | Stage 2 has not run yet. Either trigger the DAG (which runs the stages in order) or run `python code/models/train_model.py` first. |
| Tasks show up **pink** (skipped) in the grid view | The run hit `dagrun_timeout`; Airflow skips whatever has not finished. Check how long `deploy_api_and_app` took — if it is minutes rather than seconds, the Docker layer cache is being evicted and every build is reinstalling the scientific stack from PyPI. |
| Streamlit says *API unreachable* | The `api` container is still starting; the app waits for its healthcheck, so simply reload in 20 s. |

## 8. Grading checklist

| Criterion | Where it lives |
|---|---|
| Data engineering implemented and working | `code/datasets/prepare_data.py`, task `data_engineering`, outputs in `data/processed/` |
| Model engineering implemented and working | `code/models/{features,train_model}.py`, task `model_engineering`, metrics in `models/metrics.json` and MLflow |
| Deployment in two separate containers, app shows API predictions | `code/deployment/`, containers `pmldl-api` and `pmldl-app`, verified by task `smoke_test` |
| Pipeline automated on schedule | `services/airflow/dags/pmldl_pipeline_dag.py`, `schedule="*/5 * * * *"` |
| Repository structured | the layout in section 2 |
